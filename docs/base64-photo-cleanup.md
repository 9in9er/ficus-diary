## Проверка production и вишлиста

20 ноября 2026 года прочитаны публичная страница `https://ficus-diary.ru/`
(перенаправляет на `https://www.ficus-diary.ru/`) и карта исходников опубликованной
сборки `/static/js/main.ec36d3ac.js.map`. Вход в аккаунт не выполнялся.
До локального исправления следующие исходники в карте совпадали с рабочим деревом:

- `src/hooks/usePlantPhoto.js`;
- `src/hooks/usePlantDraft.js`;
- `src/hooks/usePlants.jsx`;
- `src/components/PlantPhoto.jsx`;
- `src/components/WishlistForm.jsx`;
- `src/components/WishlistCard.jsx`.

Просмотр карточек коллекции и вишлиста работает без `photo`: `PlantPhoto` использует
`usePlantPhoto`, который запрашивает `/api/photos` по ID растения. Сервер читает `photoKey`,
проверяет его путь и выдаёт URL. Изменение обычных полей через `savePlant` и `saveWish`
отправляет только изменяемые метаданные; поле `photo` для сохранения не требуется.
Замена изображения использует новый Blob и текущий ключ, без зависимости от старого base64.

Обнаруженная в этой production-сборке несовместимость касалась **предпросмотра при редактировании вишлиста**:

- `usePlantDraft.resetDraft` заполнял `draft.photo` только из `plant.photo`, не переносил
  ключ и ID в модель предпросмотра;
- `WishlistForm` показывал `<img>` только при наличии `draft.photo` и не получал
  изображение по `photoKey`;
- после удаления `photo` карточка продолжит показывать объект, а предпросмотр
  в форме редактирования исчезнет. Это ухудшение сценария, хотя сам объект в S3 остаётся.

Локально исправлены `usePlantDraft`, `WishlistForm` и общий `PlantPhoto`:
черновик сохраняет ID/ключ для предпросмотра, а форма использует существующий механизм
получения и обновления временных ссылок. Выбранный новый Blob показывается через локальный
Object URL, который освобождается при замене, отмене и закрытии формы. Внешний вид,
CSS-классы и поддержка base64 без ключа сохранены. Ни URL, ни base64 не добавляются
в сохраняемые метаданные.

`src/hooks/photoCleanupCompatibility.test.jsx` проверяет предпросмотр без поля `photo`,
повтор при ошибке ссылки, legacy-режим и сохранение метаданных. `Wishlist.test.jsx`
проверяет создание с фото, редактирование и замену без `photo`, опоздавший ответ,
освобождение Blob URL, отмену, перенос в коллекцию и legacy-фото в корзине.
Серверный тест подтверждает сохранение статуса вишлиста при замене фото без base64.
Дополнительных обязательных зависимостей от base64 в интерфейсе не найдено:
остальные обращения к `photo` используются как совместимый резервный источник.
Firestore Rules не менялись; новая версия не публиковалась.

Чтобы разблокировать удаление, нужно отдельно выпустить подготовленное исправление
и подтвердить карточки/редактирование/замену фото/вишлист без `photo` в production. Затем отдельно
пересмотреть `APPLICATION_COMPATIBILITY` в скрипте, повторить dry-run и убедиться,
что старые вкладки обновлены. Одного изменения константы без проверки приложения недостаточно.

## Команды Windows PowerShell

Из корня проекта, Node.js 24, серверные настройки из существующей `.env.local`.

**1. Dry-run всех кандидатов — доступен сейчас:**

```powershell

```

Это чтение Firestore и HEAD/GET объектов S3 с полной локальной декодировкой.
Транзакций записи нет. При исходных данных из задачи ожидаются 265 проверенных
кандидатов и 0 удалённых полей. Это ожидание по предоставленным результатам,
а не результат заново запущенного облачного сканирования.
Из-за блокировки совместимости `compatibilityPassed: false`, `readyToApply: false`
и код выхода `2` сохранятся даже при успешной проверке всех объектов.

**2. Первые пять кандидатов — команда на будущее, сейчас заблокирована:**

```powershell
npm.cmd run cleanup:photos -- --project my-plants-app-8f6fc --apply --limit 5 --stop-on-error
```

**3. Продолжить для оставшихся — команда на будущее, сейчас заблокирована:**

```powershell
npm.cmd run cleanup:photos -- --project my-plants-app-8f6fc --apply --stop-on-error
```

Команды 2 и 3 при подготовке не запускались. После снятия блокировки в рамках
отдельно проверенного изменения вторая команда удалит не более пяти полей,
а третья пропустит уже очищенные документы и продолжит с оставшихся.
Между партиями необходимо проверить результат первых пяти в приложении,
включая вишлист, и сохранить актуальную независимую резервную копию.

## Условия и порядок обработки

Проект жёстко ограничен `my-plants-app-8f6fc`. Обязательный `--project` проверяется
против окружения, инициализированных Admin SDK/Firestore и базы `(default)`;
конфликтующие проекты и эмуляторы отвергаются. Подключение к S3 использует
существующие `YANDEX_*` и разрешает только HTTPS endpoint Yandex Object Storage.

Обработка последовательная, по ID, страницами по 100. Статистика охватывает коллекцию
`plants` всех владельцев, включая вишлист. Проекция читает только поля, необходимые
для проверки; заметки и истории ухода не выгружаются. Пропускаются:

- документы с непустым `deletedAt` — все 47 растений корзины должны сохраниться;
- документы с `_photoDeleting` (в том числе `true`);
- документы без `photoKey` или с `photoKey: null`;
- документы без `photo` с префиксом `data:image/...;base64,`, включая уже очищенные.

Пустой/некорректный ненулевой ключ при наличии base64 не перезаписывается и считается
ошибкой. Для каждого выбранного кандидата проверяются UID, ID, точный путь
`plants/<SHA-256(userId)>/<id>/photos/<имя>.webp`, затем существующий `verifyObject` выполняет:

1. HEAD: размер от 1 байта до 5 МиБ, MIME `image/webp`, наличие ETag.
2. GET с `IfMatch`: объект полностью читается, ETag и заявленные/фактические размеры совпадают.
3. Проверку SHA-256, если метаданные присутствуют.
4. Проверку RIFF/WEBP и полную декодировку пикселей через Sharp:
   один кадр, не более 1600 × 1600, с ограничением памяти/размера/времени чтения.

404, отказ в доступе, ошибки чтения, тайм-аут, неверные размеры, контрольные суммы
и повреждение изображения предотвращают удаление поля и имеют отдельные безопасные коды.
Неправильный путь также предотвращает обращение к чужому объекту.

В режиме apply после успешной проверки объекта транзакция Firestore заново читает
документ. Проверяются существование, неизменность `userId`, `photo` и `photoKey`,
отсутствие корзины и блокировки, base64 и корректность пути. При повторе транзакции
проверки выполняются заново. Единственная запись:

```javascript
tx.update(ref, { photo: FieldValue.delete() });
```

`photoKey`, владелец, вишлист, заметки, поливы, удобрения и прочие поля сохраняются.
Конкурентные изменения заметок допускаются и не перезаписываются. Изменение
проверяемых полей или состояния растения отменяет удаление. Файлы S3 не меняются:
скрипт не вызывает PUT/DELETE, листинг или создание подписанных URL.

`--limit 5` ограничивает **пять попыток обработки кандидатов**, включая ошибки:
удалений будет не более пяти даже при потерянном ответе о записи. Обычные пропуски
лимит не расходуют. После достижения лимита скрипт только дочитывает страницы
для подсчёта отложенных кандидатов, не проверяя их объекты и не изменяя документы.
Поэтому «подходит» относится только к успешно проверенной части.

Без `--stop-on-error` ошибка растения учитывается, а обработка продолжается.
С флагом скрипт останавливается сразу, и `scanComplete` становится `false`.
Ошибка страницы Firestore всегда останавливает проход. Потеря ответа о commit
отмечается как `FIRESTORE_FAILED_OR_OUTCOME_UNKNOWN`: удаление могло состояться,
но оно не учитывается как подтверждённое. Повтор безопасно пропустит отсутствующий `photo`.

Firestore и S3 не имеют общей транзакции. Между проверкой и удалением поля объект
теоретически может быть изменён вручную. Не запускайте параллельные миграции,
редактирование фото, удаление растений или объектов. Проверка не заменяет backup.

## Итоговый JSON-отчёт

По каждому обработанному документу выводятся безопасные статус/код и ID.
Сводка `summary` содержит:

| Поле | Значение |
| --- | --- |
| `checked` | Прочитанные документы |
| `candidates` | Предварительные кандидаты по наличию полей и состоянию |
| `attempted` | Начатые проверки кандидатов в пределах лимита |
| `eligible`, `verifiedObjects` | Кандидаты с проверенными путём и объектом, до финальной проверки транзакцией |
| `dryRunPhotos` | Успешные проверки в dry-run |
| `removed` | Подтверждённые удаления поля `photo` |
| `skipped`, `skippedByReason` | Пропуски и причины |
| `deferred` | Кандидаты за пределами лимита, объекты которых не проверялись |
| `errors`, `errorsByCode`, `issues` | Ошибки и безопасные диагностические записи |
| `wishlistCandidates`, `wishlistEligible`, `wishlistRemoved` | Те же стадии для вишлиста |
| `estimatedReclaimableBytes` | Примерный объём поля `photo` у проверенных кандидатов |
| `estimatedFreedBytes` | Примерный объём только подтверждённых удалений |
| `scanComplete`, `stopped` | Полнота прохода и остановка |
| `localPreviewCompatible`, `productionVerified` | Отдельные статусы локального исправления и проверки опубликованной версии |
| `compatibilityPassed`, `applicationBlock`, `readyToApply` | Итоговая готовность; локального исправления недостаточно для разрешения удаления |

Оценка объёма — UTF-8 длина значения и имени поля плюс два терминатора.
Она не включает индексы, компрессию, накладные расходы и не является оценкой счёта.
Base64, UID, имена, заметки, ключи объектов, секреты, подписанные URL и сырые SDK-ошибки
не выводятся. Недопустимый ID заменяется SHA-256. Коды выхода: `0` — проход без
ошибок и блокировки; `1` — ошибка/неполный проход; `2` — dry-run без ошибок данных,
но с несовместимостью приложения. `--apply` с текущей блокировкой возвращает `1`.

## Тесты

```powershell
npm.cmd run test:server
npm.cmd test -- --watchAll=false --runInBand
```

Тесты удаления используют Firestore/S3 исключительно в памяти и реальный
`FieldValue.delete()` и декодер Sharp. Для моделирования будущего совместимого
релиза в тестовый runner передаются три флага `localPreviewCompatible`, `productionVerified`,
`applyAllowed` со значением `true`; в CLI такого
параметра нет. Живой процесс с `--apply` не запускается. Проверены несколько
владельцев, вишлист, неизменность корзины, ошибки S3/Firestore, изменения во время
чтения, повтор транзакции, потеря ответа, лимит и безопасный повторный запуск.
