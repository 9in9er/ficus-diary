## Совместимость и необходимость временных Rules

| Клиент и Rules | Результат |
| --- | --- |
| Новый клиент + действующие Rules | Чтение с фильтром владельца, создание без фото и обычные правки разрешены. Фото пишет Admin API, который обходит Rules. Но прямой delete и подмена служебных полей всё ещё возможны по старым Rules |
| Новый клиент + `firestore.transition.rules` | Все рабочие операции разрешены; прямой delete, смена владельца, клиентская запись `photoKey`, `_photoDeleting` и доступ к `_photoUploads` запрещены |
| Новый клиент + итоговые `firestore.rules` | Все рабочие операции разрешены; клиентские записи `photo` дополнительно закрыты |
| Старый клиент + переходные Rules | Создание растения/желания с base64/null и правки обычных полей сохранены. Изменять base64 разрешено только до появления `photoKey`. Прямое окончательное удаление/автоочистка запрещены |
| Старый клиент + итоговые Rules | Создание с `photo`, даже `null`, и изменение `photo` запрещены. Правки, которые отправляют прежнее неизменённое `photo`, проходят, поскольку Rules сравнивают изменённые поля. Удаление запрещено |

Переходные Rules нужны **до** переключения production-кода: флаг API не может
остановить `deleteDoc` из уже открытой старой вкладки. Старый клиент автоматически
удалял документы корзины старше 30 дней. Полностью сохранить это поведение и
одновременно запретить окончательное удаление невозможно. На старой вкладке
может появиться сообщение об отказе автоочистки/удаления; обновление страницы
после выпуска убирает старый код. Чтение и повседневные действия сохраняются.

Если у документа уже есть `photoKey`, старая вкладка показывает только прежнее
base64 (или не показывает фото у нового S3-документа). Замена фото в такой вкладке
намеренно запрещена переходными Rules: иначе сохранение выглядело бы успешным,
а новый клиент продолжал бы показывать прежний S3-объект. Нужно обновить страницу.

## Что изменено при подготовке

- `firestore.transition.rules`: временная совместимость со старым `photo` при защите
  серверных полей и полном запрете клиентского удаления.
- `server/photos.cjs`: `PERMANENT_DELETE_RELEASE_ENABLED=false` блокирует удаление
  в публичном API независимо от env. `ENABLE_PERMANENT_PLANT_DELETE=false` также
  добавлен в локальную `.env.local`; оставьте это значение и в Vercel.
- Для будущего включения удаления потребуется отдельное изменение константы,
  проверка сценария и новый релиз. Простое переключение env не включит удаление.
- `.gitignore` и `.vercelignore` дополнены исключениями файлов приватных ключей.
- `scripts/check-release-secrets.cjs`: локальная проверка кандидатов Git, индекса,
  достижимой истории и build без вывода ключей. Она ищет доступные локальные
  секреты и признаки приватных ключей/service account, а не гарантирует обнаружение
  любого неизвестного секрета. Локальных Yandex-ключей нет, их точные значения
  проверить по этому файлу невозможно. Серверные секреты не имеют `REACT_APP_`.
- Добавлены тестовая копия прочитанных production Rules и 7 проверок перехода.
  Тестовые файлы выполняются последовательно, поскольку используют один demo-проект.

## Порядок публикации владельцем

Следующие действия — инструкция на будущий выпуск; сейчас они не выполнялись.

1. **Зафиксировать точки возврата и проверить Vercel.** Сохранить URL текущего
   production deployment и его SHA из Vercel, текст действующих Rules и независимый
   backup. Локальный HEAD не доказывает, какой SHA сейчас обслуживает production.
   В проекте `my-plants-app` подтвердить Git repo и Production Branch `main`, домен
   `ficus-diary.ru`, CRA/build/Node 24. Проверить Production env: оба project ID
   равны `my-plants-app-8f6fc`, учётная запись Admin от того же проекта,
   `ENABLE_PERMANENT_PLANT_DELETE=false` без внешних кавычек. Проверить точный
   production origin в уже настроенном CORS. Env применяются при новой публикации.

2. **Подготовить commit в отдельной ветке.** В PowerShell из корня репозитория:

   ```powershell
   git switch -c release/yandex-object-storage
   node scripts/check-release-secrets.cjs
   git add .gitignore .vercelignore .env.example README.md package.json package-lock.json vercel.json firebase.rules-test.json firestore.rules firestore.transition.rules api server src scripts tests docs
   git diff --cached --check
   git diff --cached --name-only
   git diff --cached --stat
   node scripts/check-release-secrets.cjs
   git commit -m "feat: prepare Yandex Object Storage release"
   ```

   В списке не должно быть `.env.local`, `backups/`, `.vercel/` или ключей.
   Не использовать `git add -f`. Если Git сообщает dubious ownership, выполнять
   операции от обычного владельца репозитория; для чтения в этой проверке
   использовался разовый `git -c safe.directory=...`, глобальный конфиг не менялся.

3. **Проверить облачный Preview до production.** Рекомендуется отдельный тестовый
   Firebase-проект и тестовый аккаунт. Только для release-ветки в Preview задать
   его web-конфигурацию и Firebase Admin, Yandex env и флаг `false`; не оставлять
   унаследованную production web-конфигурацию вместе с тестовым Admin. Production
   env не менять. Добавить точный origin Preview в CORS и при необходимости
   Firebase Auth Authorized domains. После этого выполнить вручную:

   ```powershell
   git push -u origin release/yandex-object-storage
   ```

   Vercel автоматически создаст Preview. Создать PR в `main`, пока не сливать.
   Убедиться в deployment, что это Preview и правильный SHA. Сначала применить
   переходные Rules **только к тестовому проекту**, проверить создание с фото,
   чтение после reload, замену, сетевой сбой/повтор, вишлист, полив/заметки,
   корзину/восстановление и отказ удаления. Затем применить итоговые Rules к тому
   же тестовому проекту и повторить основные сценарии. Проверить `/api/photos`,
   WebP PUT/GET и отсутствие ошибок Sharp/Firebase/Yandex в runtime.

   Не копировать реальные документы или фотографии. Если тестового Firebase нет,
   Preview можно проверить только без записей; полноценный облачный сценарий
   останется непроверенным. Preview с production env пишет в настоящую базу.
   До принятия этого ограничения production-выпуск отложить.

4. **Перед переключением кода опубликовать переходные Rules.** Открыть Firebase
   Console → `my-plants-app-8f6fc` → Firestore → база `(default)` → Rules.
   Ещё раз сравнить активные Rules с тестовой копией. Если правила за это время
   изменились или появились другие используемые коллекции, остановиться и сверить
   новые условия. Полностью заменить текст на `firestore.transition.rules`,
   опубликовать. Не добавлять его вторым широким `match`: разрешающие правила
   объединяются, запрет `delete` не перекрывает старый `allow write`.
   Дождаться распространения и проверить чтение текущего приложения; для тестов
   записи использовать тестовый проект. Firebase указывает до минуты для новых
   запросов/listeners и до 10 минут для существующих listeners. Защита не отменяет
   операции, которые успели завершиться до её применения.

5. **Выпустить код через GitHub.** После успешного Preview и переходных Rules
   слить проверенный PR в `main`. Push/merge в подтверждённую Production Branch
   автоматически запускает production build и переключение домена в Vercel.
   Отдельный `vercel --prod` не нужен. Не нажимать Redeploy старого SHA вместо
   выпуска нового кода. Дождаться `Ready`, сверить SHA, Node runtime и наличие
   функции `/api/photos`; открытие GET этого пути должно возвращать JSON 405,
   POST без токена — 401 (без записи). Проверить вход и отображение прежних фото
   на production, не редактируя существующие документы. Полный сценарий с новым
   production-тестовым растением допустим лишь после отдельного решения владельца;
   в рамках текущего запрета реальных записей он не выполняется.

6. **Оставить переходные Rules на период обновления вкладок.** Предложить
   пользователям обновить страницу. Старые вкладки могут жить долго: фиксированное
   ожидание, даже сутки, не доказывает, что их больше нет. До готовности завершить
   поддержку старого создания/замены base64 сохранить переходные Rules. Они уже
   запрещают окончательное удаление и защищают `photoKey`/владельца/служебные поля.

7. **Завершить переход.** После проверки новой версии и выбранного периода
   совместимости заменить production Rules целиком на `firestore.rules` в той же
   Firebase Console. Это отдельная публикация Rules; GitHub/Vercel её не выполняет
   (в репозитории нет workflow деплоя Firebase). Дождаться распространения,
   проверить чтение, основную работу нового клиента и ожидаемые отказы по локальным
   тестам. Старым вкладкам для создания/изменения фото теперь необходимо обновление.
   Флаг и блокировку окончательного удаления оставить выключенными.

## Возврат при проблеме

При отказах после ужесточения Rules сначала вернуть `firestore.transition.rules`,
сохранив новый код. Не возвращать широкий `allow read, write`: он снова разрешит
старым вкладкам окончательно удалять документы. Дождаться распространения правил.

Если проблема в приложении, использовать сохранённый предыдущий deployment через
Vercel Instant Rollback, оставив переходные Rules. На Hobby доступен возврат к
непосредственно предыдущему production deployment. Rollback Vercel не откатывает
Firestore, Rules или бакет и использует конфигурацию старой сборки. Старый клиент
не показывает S3-only фото, а для растений с обоими полями покажет сохранённое
прежнее base64; это ограниченный аварийный возврат, до исправления нового клиента.
Файлы и `photoKey` не удалять. После Instant Rollback проверить состояние
auto-assignment доменов: Vercel отключает его до отмены rollback.

Не восстанавливать backup поверх действующей базы автоматически: это может
перезаписать изменения пользователей после снимка. Миграцию не запускать.

## Старые фотографии

Документы только с `photo` показываются непосредственно из base64, без `/api/photos`
и Yandex. Обычное редактирование, уход, корзина и восстановление не меняют `photo`.
Замена фото через новый API добавляет/меняет только `photoKey` и поля формы,
сохраняя старое `photo` и предыдущие объекты. Новый клиент предпочитает S3-фото,
но при ошибке использует сохранённый base64. Rules не преобразуют документы.

Новые фотографии при успешной загрузке записываются в Yandex; автоматической
миграции, фоновой очистки или удаления старого base64 в сборке и API нет.
После завершения production-миграции одноразовые инструменты переноса и очистки
удалены. Для проверки целостности фотографий сохранена команда `verify:photos`;
текущая инструкция — [object-storage.md](object-storage.md#7-проверка-целостности-фотографий).
