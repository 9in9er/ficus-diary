# Совместимость Firestore Rules с ficus-diary

Проверены все рабочие исходники в `src`, `api`, `server`, `scripts`.
Окончательные правила находятся в [firestore.rules](../firestore.rules).
В пятом этапе уборки их разрешения и ограничения не менялись; production-база,
опубликованные Rules и существующие фотографии не изменялись.

Миграция фотографий и переход клиента завершены. Переходные правила, fixture
старого состояния production и отдельный набор тестов перехода удалены.
Проверка неизменённых защищённых полей перенесена в основной набор
`tests/firestore/plants.rules.test.cjs`; запреты их записи сохранены и дополнены
проверками `photo: null` для растений и вишлиста с `photoKey` и без него.
История первого выпуска: [production-release.md](production-release.md).

## Все места записи в plants

| Источник | Операции |
| --- | --- |
| `src/hooks/usePlants.jsx`, `createPlant` | Клиентский `addDoc`: новое растение без фото |
| `src/hooks/usePlants.jsx`, `createWish` | Клиентский `addDoc`: желание без фото |
| `src/hooks/usePlants.jsx`, `updatePlant` | Единственный клиентский `updateDoc`; через него идут все перечисленные ниже изменения |
| `server/photos.cjs`, `commit` | Firebase Admin `runTransaction`: `tx.create` растения/желания с фото или `tx.update` при замене фото |
| `server/photos.cjs`, `delete` | Две Firebase Admin транзакции: `tx.update({_photoDeleting: true})`, затем `tx.delete` после удаления файлов |

Клиентских `setDoc`, `deleteDoc`, `runTransaction` и `writeBatch` в рабочем
приложении больше нет. В тестах эти вызовы используются для проверки запретов.
Серверный `.set` в `photos.cjs` относится к `_photoUploads`, а не к `plants`.
`doc(collection(db, 'plants'))` при подготовке загрузки только генерирует ID,
ничего не записывает.

## Поля клиентского создания

| Путь | Точные поля |
| --- | --- |
| Обычное растение, `createPlant` | `name`, `acquiredAt`, `wateringLog`, `fertilizingLog`, `notes`, `userId`, `createdAt`, `pinned`, `hidden`, `deletedAt` |
| Вишлист, `createWish` | `name`, `description`, `price`, `links`, `isWishlisted`, `userId`, `createdAt`, `deletedAt`, `hidden`, `pinned` |

В итоговом `allow create` разрешено объединение этих полей и необязательное
`replanted`. Сейчас `createPlant` и `createWish` его не передают: оно впервые
появляется при переключении пересадки или переносе желания в коллекцию.
Следовательно, отсутствие `replanted` в прежнем `allow create` не блокировало
текущие формы, но асимметрия исправлена для согласованности схемы.
Отсутствие `replanted` по-прежнему разрешено; старые документы обновлять не нужно.

## Все клиентские обновления

| Действие / функция в usePlants | Изменяемые поля |
| --- | --- |
| Редактирование растения, `savePlant` | `name`, `acquiredAt` |
| Редактирование желания, `saveWish` | `name`, `description`, `price`, `links` |
| Полив / удаление полива | `wateringLog` |
| Удобрение / удаление удобрения | `fertilizingLog` |
| Добавление / удаление заметки | `notes` |
| Пересадка, `toggleNeedReplant` | `replanted` |
| Закрепление / открепление | `pinned` |
| Скрытие / показ | `hidden` |
| В корзину, `handleDeletePlant` | `deletedAt`, `hidden`, `pinned` |
| Восстановление, `restorePlant` | `deletedAt` |
| «Уже у меня», `acquireWish` | `isWishlisted`, `acquiredAt`, `createdAt`, `wateringLog`, `fertilizingLog`, `notes`, `pinned`, `hidden`, `replanted`, `deletedAt` |

Поливы и удобрения — массивы ISO-строк. Элемент `notes` содержит `id`, `text`,
`createdAt`; это вложенные данные одного разрешённого поля `notes`, а не
дополнительные поля документа. `links` — массив нормализованных HTTP(S) ссылок.
`createdAt` оставлен разрешённым при update: `acquireWish` обновляет эту дату.
Все реальные поля перечисленных операций присутствуют в `allow update`.

## Серверные операции и фото

При создании с фото сервер записывает обычные поля растения/желания, `userId`,
`isWishlisted`, `createdAt`, `deletedAt`, `hidden`, `pinned` и `photoKey`;
для обычного растения также создаёт `wateringLog`, `fertilizingLog`, `notes`.
Замена фото обновляет `name` и `acquiredAt` либо поля вишлиста, плюс `photoKey`.
Окончательное удаление добавляет `_photoDeleting` и затем удаляет документ.
Миграция фотографий завершена; клиентское отображение по старому `photo` удалено.

Эти операции используют **Firebase Admin SDK**, который обходит клиентские
Security Rules. Поэтому добавлять `photoKey`/`_photoDeleting` в клиентские
списки разрешений не нужно. Проверка Firebase ID Token, UID владельца,
ключей объектов, корзины и блокировки удаления находится в `server/photos.cjs`.

При обновлении Rules сравнивают только изменённые поля (`diff().affectedKeys()`),
поэтому уже имеющиеся `photo`, `photoKey` и неизвестные исторические поля не
мешают менять название, поливы и т. п. Они сохраняются без изменений.
Полная перезапись через `setDoc`, удаляющая защищённые поля, запрещена.

## Сохранённые ограничения

- Читать документы и менять разрешённые поля может только их владелец.
  Запрос приложения с `where('userId', '==', uid)` разрешён; чтение всей чужой
  коллекции без ограничения владельца запрещено.
- При создании `userId` должен совпадать с UID текущего пользователя.
  При обновлении он явно должен остаться прежним и исключён из списка изменений.
- Клиент не может добавлять, менять или удалять `photo`, `photoKey`,
  `_photoDeleting`. Нельзя сменить или удалить `userId`.
- `_photoDeleting: true` блокирует клиентские обновления, включая восстановление.
- Клиентский `deleteDoc` всегда запрещён; окончательное удаление идёт через API.
- `_photoUploads`, подколлекции растений и остальные коллекции закрыты.

Новых ограничений типов и обязательных полей не добавлено: это отдельная задача,
которую нужно согласовывать с историческими данными. Удалять неизвестные старые
поля или преобразовывать документы для применения этих правил не требуется.

## Локальные тесты Rules

Добавлены `tests/firestore/plants.rules.test.cjs`, `firebase.rules-test.json`
и dev-зависимости `@firebase/rules-unit-testing` (ветка 5 для Firebase 12),
`firebase-tools`. Нужны Node.js 24 и **Java 21 или новее** в PATH.
Проверьте `java -version`: один `JAVA_HOME` при старой Java в PATH недостаточен
для текущей версии Firebase CLI. Переносимую Java можно выбрать только для
текущего окна PowerShell, не меняя системные настройки:

```powershell
$env:JAVA_HOME = 'C:\path\to\java-21'
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
```

```powershell
npm.cmd ci
npm.cmd run test:rules
```

Команда запускает только локальный Firestore Emulator на `127.0.0.1:8080`
с фиктивным project ID `demo-ficus-diary-rules`, выполняет тесты и останавливает
эмулятор. Вход в Firebase, сервисные ключи, `.env.local` и облачные ресурсы не
нужны. При первом запуске Firebase CLI скачивает эмулятор. Production-проект
не выбирается: конфигурация и ID заданы явно в npm-команде. Тесты дополнительно
отказываются работать без локального `FIRESTORE_EMULATOR_HOST` или с другим
`GCLOUD_PROJECT`.

Проверяются создание обоих видов растений, необязательное `replanted`, все
обычные обновления, владелец/чужой пользователь/отсутствие авторизации,
защищённые поля при create/update/merge/full set/transaction/batch, корзина,
блокировка удаления, приватность `_photoUploads`, совместимость старых фото
и редактирования после серверной загрузки.

Неизменённые защищённые поля не мешают правкам метаданных. Клиент не может
добавить даже `photo: null` при создании или обновлении документа. Исторические
значения в искусственных данных проверяют ограничения Rules, а не поддержку
старого формата фотографий в приложении.

Отдельный интеграционный тест вызывает **настоящий сервис** `createPhotoService`
с реальным Admin SDK и локальными транзакциями Firestore Emulator: создание
растения и желания с фото, замена фото, окончательное удаление. Вызовы S3 в нём
заменены локальными заглушками; реальный бакет и существующие документы не
затрагиваются.

Официальные основания:
[ограничение изменяемых полей](https://firebase.google.com/docs/firestore/security/rules-fields),
[тестирование Rules в эмуляторе](https://firebase.google.com/docs/firestore/security/test-rules-emulator).

## Готовность final rules после миграции — 20.11.2026

**Вывод: проверенные `firestore.rules` совместимы с текущим production-клиентом;
обязательных изменений кода перед переходом с transition rules нет.**
Правила не требуют наличия `photoKey` и не запрещают сохранённый base64.
Они запрещают клиенту создавать, добавлять, изменять или удалять поле `photo`.
Повторная передача неизменённого существующего значения разрешена.

Состояние production-данных принято из итогового отчёта владельца: 316 документов,
266 проверенных объектов и `photoKey`, 0 пар `photo` + `photoKey`, 0 активных base64
без ключа, 47 base64 без ключа в корзине, 3 документа без фото, ошибок и замечаний нет.
Нового чтения документов Firestore и объектов бакета в этой проверке не было.
Действующая облачная версия Rules повторно не считывалась: сравнивались локальные
`firestore.transition.rules` и `firestore.rules`. Исторический production fixture
от 10.12.2025 не является подтверждением текущих облачных правил.

### Разница правил и операции

В final из списков create/update исключён `photo`; удалено переходное условие,
разрешавшее его изменение только до появления `photoKey`. Остальные разрешения
совпадают: только владелец, неизменяемый `userId`, защита `photoKey` и `_photoDeleting`,
блокировка обновлений при удалении, запрет прямого delete и закрытые прочие коллекции.

| Операция | Результат с final rules |
| --- | --- |
| Создание растения/желания без фото | Разрешено: приложение не отправляет `photo`, даже `null` |
| Создание с фото, замена фото | Через Admin API, независимо от клиентских Rules; авторизация и проверки владельца остаются в API |
| Название, дата, описание, цена, ссылки | Разрешено; защищённые фото-поля не переписываются |
| Поливы, удобрения, заметки: добавление/удаление | Разрешено через соответствующие поля одного документа |
| Пересадка, закрепление, скрытие | Разрешено |
| Корзина / восстановление | Разрешено через `deletedAt`, при переносе также `hidden`/`pinned` |
| Вишлист → коллекция | Все поля `acquireWish` разрешены, включая `createdAt` и `replanted` |
| Документы только с `photoKey` / совсем без фото | Все обычные операции разрешены |
| Окончательное удаление | Прямой delete запрещён; публичный API дополнительно отключён константой релиза |

### Восстановление 47 растений

`restorePlant` отправляет только `{ deletedAt: null }`. `diff().affectedKeys()`
не включает неизменённое `photo`, поэтому восстановление разрешено, base64 и история
ухода сохраняются. `usePlantPhoto` показывает `plant.photo` без обращения к API,
если `photoKey` отсутствует. Это одинаково работает для коллекции и вишлиста.
При `_photoDeleting: true` восстановление намеренно запрещено обоими наборами Rules.

**Восстановление не выполняет миграцию.** После него счётчик
`activeBase64WithoutPhotoKey` увеличится, и проверка миграции сообщит о замечании.
Это ожидаемое следствие возврата старого документа, а не потеря фотографии или отказ
Rules. Замена фотографии через API после восстановления добавляет `photoKey`,
сохраняя прежний base64. Автоматического переноса исходного фото при восстановлении
в коде нет; если понадобится постоянный инвариант «все активные фото только в S3»,
это отдельная задача и отдельное изменение кода.

### Проверки и границы подтверждения

- Rules: **42/42**, Java 21, локальный `demo-ficus-diary-rules`. Дополнительно
  проверены все 17 операций на документах только с ключом и без фото; 47 синтетических
  восстановлений с полным сравнением сохранённых полей; отказ старой форме,
  добавляющей `photo: null`; замена фото восстановленного base64-документа через
  настоящий Admin SDK/сервис с заглушкой S3.
- Клиент: **118/118**, 16 suites. Включены показ legacy-фото без API, показ и
  предпросмотр по ключу без base64, отсутствие автоматической очистки корзины.
- Сервер: **100/100**. Проверены авторизация, владение, загрузки/повторы,
  защита корзины/удаления и сохранение прежнего фото при замене.
- Публичная production-страница `https://www.ficus-diary.ru/` вернула HTTP 200,
  bundle `/static/js/main.011c54fe.js`. Из его source map прочитаны и сравнены
  с локальными файлами `hooks/usePlants.jsx`, `hooks/usePlantPhoto.js`,
  `hooks/usePlantDraft.js`, `components/WishlistForm.jsx`, `services/plantPhotos.js`:
  все пять совпадают после нормализации переводов строк. Это проверка фактически
  выдаваемого клиентского кода; серверный deployment и облачные Rules этим не проверяются.
- Живые операции приложения с production Firestore/S3 не выполнялись. Старые
  уже открытые вкладки могут содержать прежний код: создание с `photo`, даже `null`,
  замена base64 и добавление `photo: null` в очищенный документ будут запрещены.
  Требуется перезагрузить такие вкладки. Неизменённое существующее `photo` не мешает
  обычному обновлению, но отсутствующее поле и `photo: null` различаются для final.

Локально дополнены только тесты и этот отчёт; код приложения и оба набора Rules
не изменялись. Firebase и Object Storage не изменялись; публикаций и удаления
production-документов/фотографий не было.

**Один следующий безопасный шаг сейчас:** выполнить в Firebase Console только
чтение и сверку действующих Rules с `firestore.transition.rules`, сохранив их копию
для возврата. После подтверждения совпадения технических блокеров для отдельной
публикации проверенного `firestore.rules` нет; до этой сверки фактическое облачное
состояние не следует считать независимо подтверждённым этой проверкой.
