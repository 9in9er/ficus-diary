# Однократная обработка существующих фотографий

Инструменты только подготовлены. В рамках реализации не запускались даже облачные
dry-run: все проверки используют синтетические данные, локальный sharp и имитацию S3/Firestore.
Правила Firestore, оригиналы и пользовательские документы не изменяются.

Используется Node.js 24, существующие зависимости и настройки `.env.local`.
Явный `--project` обязан совпадать с Firebase-проектом окружения и Admin SDK.
Работа идёт последовательно, страницами по 100 документов, по всей коллекции `plants`:
все владельцы, обычные растения, вишлист и корзина. Отдельных коллекций не создаётся.

## Диагностика — только чтение Firestore

```powershell
npm.cmd run diagnose:photo-storage -- --project my-plants-app-8f6fc
```

Новый `scripts/diagnose-photo-storage.cjs` не обращается к Object Storage.
Отчёт `summary` содержит:

| Поле | Значение |
| --- | --- |
| `documents` | Все прочитанные документы |
| `withPhotoKey`, `withThumbnail` | Наличие соответствующего поля, кроме отсутствия/`null` |
| `missingThumbnail` | Есть `photoKey`, отсутствует или равен `null` `photoThumbKey` |
| `base64Photos`, `base64WithPhotoKey` | Base64 в `photo`; из них с `photoKey` |
| `externalPhotos` | Корректные HTTP/HTTPS URL в `photo` |
| `estimatedBase64Bytes`, `estimatedBase64MiB` | Оценка размера поля: UTF-8 значения + имени + терминаторов |
| `bySection` | Те же счётчики отдельно для обычных растений, вишлиста и корзины |
| `processed`, `skipped`, `errors`, `scanComplete` | Полнота и результат сканирования |

Разделы не пересекаются: удалённое желание учитывается в корзине. Счётчики наличия
ключа не подтверждают корректность пути и существование объекта. Оценка байтов не
включает индексы, сжатие сервиса и не является расчётом стоимости Firestore.

## Миниатюры — отдельный скрипт

Новый `scripts/backfill-photo-thumbnails.cjs` пропускает имеющийся `photoThumbKey`,
отсутствующий `photoKey` и блокировку `_photoDeleting`. Растения в корзине включены.
Ошибочные ключи, чужой префикс и недоступные/повреждённые оригиналы дают ошибку
конкретного документа; следующие документы продолжают обрабатываться.

Dry-run по умолчанию, без PUT и транзакций записи:

```powershell
npm.cmd run backfill:photo-thumbnails -- --project my-plants-app-8f6fc --dry-run
```

Основная версия проверяется через HEAD + GET с `IfMatch`, ограничением размера,
таймаутом, проверкой MIME/контрольной суммы при её наличии и полным декодированием.
Из тех же байтов существующий `createPhotoThumbnail` создаёт WebP до 300 px,
качество 75; маленькие изображения не увеличиваются. Dry-run выполняет эту работу
в памяти и сообщает размер миниатюр, но ничего не сохраняет.

Реальная запись включается только явным `--apply`:

```powershell
# Первые 10 кандидатов (ошибки также расходуют лимит):
npm.cmd run backfill:photo-thumbnails -- --project my-plants-app-8f6fc --apply --limit 10

# Все оставшиеся кандидаты, когда будет отдельно решено выполнить обработку:
npm.cmd run backfill:photo-thumbnails -- --project my-plants-app-8f6fc --apply
```

Миниатюра получает отдельный UUID-совместимый путь `plants/{хеш UID}/{plantId}/photos/{id}.webp`
в существующем приватном бакете. Детерминированное имя зависит от исходного `photoKey`
и содержимого миниатюры. Перед PUT выполняется HEAD: подходящий существующий объект
переиспользуется по размеру, MIME и SHA-256; несовпадение/ошибка доступа запрещает перезапись.
Основной объект никогда не перезаписывается и не удаляется.

Транзакция повторно проверяет владельца, исходный `photoKey`, отсутствие миниатюры
и блокировки. Она добавляет только `photoThumbKey`; остальные поля, включая base64,
внешние URL, статус корзины и вишлиста, сохраняются. Повтор после частичного выполнения
пропускает готовые документы или использует уже загруженную миниатюру без нового PUT.

Отчёт: `checked`, `candidates`, `attempted`, `processed`, `created`, `dryRunPhotos`,
`skipped`, `deferred`, `errors`, причины пропусков/ошибок, `estimatedThumbnailBytes`,
`uploadedBytes`, `reusedObjects`, `scanComplete`. Лимит ограничивает попытки кандидатов;
после него сканирование продолжается только для подсчётов. `--stop-on-error` необязателен.

## Очистка base64 — существующая отдельная операция

Расширен `scripts/cleanup-base64-photos.cjs`: новый явный `--include-trash` включает
корзину. Без него сохраняется прежнее поведение — корзина пропускается.
`_photoDeleting` пропускается всегда. Внешние URL и base64 без перенесённого объекта
никогда не удаляются. Наличие миниатюры не заменяет обязательную проверку основной версии.

```powershell
# Чтение/проверка всех кандидатов, включая корзину, без удаления:
npm.cmd run cleanup:photos -- --project my-plants-app-8f6fc --dry-run --include-trash
```

Удаление поля допускается только после проверки владельца/пути и полного HEAD/GET/WebP
основного объекта. Транзакция повторно проверяет неизменность `photo`, `photoKey`,
владельца, статуса корзины и отсутствие блокировки. Удаляется только `photo` через
`FieldValue.delete()`. `photoKey`, `photoThumbKey`, пользовательские документы и S3
при этой операции никогда не изменяются.

Существующая защита production сохранена: `--apply` требует текущего файла
подтверждения опубликованного совместимого интерфейса и SHA-256 именно этого файла.
Основание и формат описаны в [base64-photo-cleanup.md](base64-photo-cleanup.md) и
`scripts/photo-cleanup-production-confirmation.cjs`. Локальная сборка и её тесты не
подтверждают состояние опубликованного приложения. Не создавайте фиктивное подтверждение.

Когда совместимость production и резервная копия будут действительно подтверждены:

```powershell
$photoCleanupReceipt = '.photo-cleanup-confirmations/production.json'
$photoCleanupHash = (Get-FileHash -LiteralPath $photoCleanupReceipt -Algorithm SHA256).Hash.ToLowerInvariant()

# Реальное удаление поля photo у первых 5 подходящих документов:
npm.cmd run cleanup:photos -- --project my-plants-app-8f6fc --apply --include-trash --limit 5 --production-confirmation $photoCleanupReceipt --confirm-production $photoCleanupHash

# Все оставшиеся подходящие документы:
npm.cmd run cleanup:photos -- --project my-plants-app-8f6fc --apply --include-trash --production-confirmation $photoCleanupReceipt --confirm-production $photoCleanupHash
```

В отчёт добавлены `includeTrash`, `trashCandidates`, `trashEligible`, `trashRemoved`.
Остальные существующие счётчики сохраняются. Код выхода очистки `2` при dry-run
без подтверждения означает сохранённую блокировку apply, а не ошибку чтения данных.
Ошибки и неполное сканирование дают код `1`; успешный backfill/диагностика — `0`.

## Совместимость и ограничения

Клиент уже работает без `photo`: карточки предпочитают `photoThumbKey`, при его отсутствии
используют `photoKey`; увеличение и редактор используют основную версию. Внешние ссылки
и старые base64 без переноса остаются прежними. Это проверяется локальными тестами.

Не запускайте обработку параллельно с другой такой обработкой или окончательным удалением
растений. Firestore и S3 не образуют общую транзакцию: при смене исходника, потере ответа
или ошибке Firestore может остаться непривязанная миниатюра. Её нельзя удалять вслепую;
повтор с тем же исходником переиспользует файл, а существующее окончательное удаление
растения очищает весь его префикс. Для воспроизводимого повторения сохраняйте lockfile/версию sharp.
Dry-run — текущая оценка, а не снимок с гарантией неизменности будущих данных.

Локальные проверки: `npm.cmd run test:server` и `npm.cmd test -- --watchAll=false --runInBand`.
CLI с реальными `.env.local`/`--apply` в тестах не запускается.
