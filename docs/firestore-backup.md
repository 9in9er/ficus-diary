# Локальная резервная копия Firestore

Экспорт запускается только вручную. Он читает все существующие документы
верхнего уровня `plants` базы `(default)` выбранного Firebase-проекта и сохраняет
их на этом компьютере. Записей, удаления, миграции фотографий, S3-запросов и
публикации нет. Чтения Firestore могут тарифицироваться по обычным правилам.

## Запуск в Windows PowerShell

Из корня репозитория, с Node.js 24:

```powershell
npm.cmd run backup:firestore -- --project ficus-diary
```

`ficus-diary` должен быть именно **Project ID** из Firebase Console, а не именем
проекта. Аргумент обязателен и не подставляется из `.env.local` автоматически.
Скрипт сверяет его с `FIREBASE_PROJECT_ID`, проектом сервисного аккаунта,
инициализированным Admin SDK и другими заданными project-переменными.
Несовпадение останавливает запуск до чтения. Эмулятор, Vercel и CI запрещены.

Используется существующая настройка `server/firebase.cjs`:
`FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` в локальном
окружении или `.env.local`. Префикс `REACT_APP_` для секретов недопустим.
Никакие ключи не нужно вставлять в командную строку. Переменные PowerShell имеют
приоритет над `.env.local`; при конфликте проверьте их локально, не публикуя ключи.

При необходимости запуска без npm (тот же результат):

```powershell
node --env-file-if-exists=.env.local .\scripts\backup-firestore.cjs --project ficus-diary
```

Справка не подключается к Firebase:

```powershell
node .\scripts\backup-firestore.cjs --help
```

## Содержимое и точность

- Экспортируются все аккаунты, вишлист и корзина, без условий `where`, ограничений
  по владельцу и удаления полей. `notes`, `wateringLog`, `fertilizingLog`, служебные
  поля и любые неизвестные поля сохраняются полностью. Удалённые ранее записи
  истории, которых уже нет в Firestore, восстановить экспортом невозможно.
- Полная строка `photo`, включая `data:image/...;base64,`, остаётся строкой без
  перекодирования, сжатия, обрезки и преобразования фотографии.
- `documents[]` содержит отдельные `id` и `document`: пользовательское поле `id`
  внутри `document.fields` не перезаписывается. Сохраняются полное ресурсное имя,
  `createTime`, `updateTime` и все типизированные поля.
- Это [типизированный JSON Firestore](https://firebase.google.com/docs/firestore/reference/rest/v1/Value),
  а не результат `JSON.stringify(snapshot.data())`: Timestamp хранит точную
  дробную часть, GeoPoint — координаты; int64 — десятичную строку; references,
  bytes, массивы и maps сохраняют тип. `NaN` и бесконечности остаются специальными
  строковыми значениями `doubleValue`. Отрицательный ноль сохраняется.
- Существующий Admin SDK выдаёт OAuth-токен и серверный `readTime`. Документы
  читаются через официальный read-only REST `documents.list` без маски полей,
  по 50 за страницу; все страницы и отдельный `COUNT` используют тот же `readTime`.
  Так изменения во время экспорта не смешивают разные состояния базы. При
  истечении доступности снимка или сетевой ошибке запуск завершается неуспешно.
- Отдельные подколлекции и другие коллекции, Firebase Auth, Rules, индексы и
  объекты Yandex S3 не входят в эту копию. В текущем приложении заметки и история
  ухода находятся в полях `plants`. Уже существующие `photoKey` сохраняются как
  поля; для самих объектов S3 нужен отдельный backup.

## Файлы и проверка целостности

Каждый запуск создаёт новую папку:

```text
backups/plants-ficus-diary-<UTC-время>-<UUID>/
  plants.json
  integrity.json
```

`backups/` исключена через `.gitignore` и `.vercelignore`, не импортируется
клиентом и не участвует в сборке. Скрипт не имеет параметра загрузки или
произвольного выходного пути. Файлы создаются эксклюзивно; существующие копии
не перезаписываются. Используйте локальный диск, поддерживающий hard links
(обычно NTFS), поскольку публикация готового JSON использует атомарный hard link.

`integrity.json` содержит число экспортированных документов, независимый COUNT
Firestore на момент снимка, размер JSON в байтах, SHA-256, `readTime` и результат
проверки JSON. JSON проверяется потоково: фиксированная внешняя структура,
каждый документ через `JSON.parse`, разделители, отсутствие дубликатов и итоговое
количество. Все фото одновременно в память не загружаются.

Успешным считается только запуск с кодом `0`, обоими файлами и успешной повторной
проверкой. При сбое может остаться `plants.json.partial` или папка без корректного
`integrity.json`; это не подтверждённая резервная копия. Старые копии сохраняются.
Исправьте причину и выполните новый запуск; автоматического продолжения нет.

Повторная проверка полностью локальная и не загружает `.env.local` или Admin SDK:

```powershell
npm.cmd run verify:firestore-backup -- ".\backups\plants-ficus-diary-<UTC-время>-<UUID>"
```

Замените имя папки точным путём из результата запуска. В консоль выводятся только
путь и сводные показатели целостности. Данные документов, фотографии, токены,
ключи и необработанные ошибки SDK не выводятся. SHA-256 выявляет повреждение;
это не цифровая подпись и не защита от подмены одновременно JSON и manifest.

Копия содержит приватные данные в открытом виде. Git/Vercel ignore не шифруют
файл и не управляют сторонней синхронизацией: папка репозитория не должна
синхронизироваться с OneDrive/Dropbox или другим облаком. Скрипт сам ничего
туда не загружает. На Windows права наследуются от локальной папки; на POSIX
создаются каталоги `0700` и файлы `0600`. Не добавляйте `backups/` через `git add -f`.

Восстановление описано отдельно: [firestore-restore.md](firestore-restore.md).

Справочник: [чтение страниц на readTime](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/list),
[REST и OAuth](https://firebase.google.com/docs/firestore/use-rest-api).
