Сравнение выполнено с локальной резервной копией на
20 ноября, 00:43:13 МСК (`2026-11-19T21:43:13.534500000Z`).
Перед сравнением проверены JSON, количество документов, размер и SHA-256 резервной копии.

Выполнен только проекционный `runQuery` Firestore. Фотографии двух документов проверены

Миграция, очистка и облачные записи не запускались.

Оба растения активны. Владельцы, `photo`, `photoKey`, `deletedAt` и `_photoDeleting`
совпадают с резервной копией. Серверные `updateTime` также не изменились:

Оба документа существовали до копирования; это не новые записи, появившиеся после него.

Обе фотографии прошли локальную конвертацию по ограничениям миграции:
у первого растения 2547 исходных байт → 1082 байта WebP, у второго — 5037 → 2680.
В проверенном состоянии оба документа подходят для адресного переноса.

**Наиболее вероятная причина пропуска — область отбора по владельцу.**
`scripts/migrate-photos.cjs` выбирает только `userId == --user`, а
`scripts/verify-photo-migration.cjs` проверяет всех владельцев проекта.
У владельца 1 сейчас нет активных base64 без ключа. Два оставшихся документа
принадлежат другим владельцам и не попали бы в его запрос.

Это вывод по состоянию данных и коду отбора. Журнал фактических запусков с аргументом
`--user`, временем сканирования и результатами по каждому документу в рабочей папке
не найден, поэтому точную историю запусков независимо подтвердить нельзя.
При наличии такого журнала достаточно сопоставить владельца внутри процесса;
публиковать UID в отчёте не требуется.

## Почему 47 растений в корзине

| Область | В резервной копии | Сейчас |
| --- | --- | --- |
| Владелец 1 | 46 | 46 |
| Владелец 3 | 1 | 1 |
| Все владельцы | 47 | 47 |

Во всех этих документах есть base64. Состав корзины и значения `deletedAt` совпадают:
переходов в корзину, восстановлений, исчезнувших документов корзины или изменений
времени удаления между двумя снимками нет. Увеличения с 46 до 47 не было:
46 — количество у одного владельца, 47 — во всём проекте.

## Почему одновременно `photo` и `photoKey` присутствуют у 263 растений

Сейчас прочитано 316 документов, ненулевых `photoKey` — 264, пар полей
`photo` + `photoKey` — 263; все 263 старых фото в этих парах являются base64.
Документ `N7SsO0upO1XYcjmLmWDL` владельца 1 имеет `photoKey`, но не имеет поля `photo`.
В резервной копии самого этого документа не было; тогда документов было 315.
Именно он объясняет разницу счётчиков. Отсутствие старого `photo` совместимо с
созданием растения через новый загрузчик; история его создания отдельно не проверялась.

## Следующие действия

1. Сохранить старые base64. Текущая проверка не является очисткой или разрешением на неё.
2. Для будущего переноса ограничить выполнение **ровно двумя указанными ID**.
   Владелец для каждого берётся из самого документа внутри процесса, отдельно для каждого ID.
   Перед записью повторно проверить активность, отсутствие ключа и блокировки,
   а также возможность конвертации. Не применять массовый `--all` для другого владельца.
3. Для адресного переноса подготовлена отдельная команда `migrate:remaining-photos`,
   получающая владельцев из документов и выводящая обезличенный отчёт.
   Она сохраняет `photo`, использует существующий механизм детерминированных ключей
   и перед добавлением `photoKey` в транзакции повторно сверяет владельца, исходное фото
   и состояние документа. Сначала выполните dry-run; запуск `--apply` остаётся отдельным действием.
   Команды и ограничения описаны в [инструкции адресной миграции](remaining-photo-migration.md).
4. После будущего успешного переноса повторить полную проверку объектов.
   При неизменном остальном состоянии ожидания будут: 266 ключей, 265 пар
   `photo` + `photoKey`, 47 растений в корзине с base64 и 0 активных base64 без ключа.

## Повторить только диагностику

```powershell
npm.cmd run diagnose:photos -- --project my-plants-app-8f6fc --backup "backups/plants-my-plants-app-8f6fc-2026-11-19T21-43-13-771Z-945c966d-a702-49c9-995d-7fab6a19aa7d"
```

Для проверки только локальной копии, без сети, добавить `--offline`.
Скрипт выводит только флаги, типы полей, безопасные даты, размеры и псевдонимы владельцев;
base64, UID, имена, ключи объектов, секреты, токены, подписанные URL и сырые SDK-ошибки
не выводятся. Псевдонимы служат для сопоставления внутри отчёта, а не для идентификации аккаунта.
Если достоверно известен UID прежнего запуска, скрипт может сравнить его внутри процесса
через `PHOTO_MIGRATION_USER_ID`, не выводя значение; по умолчанию исторический UID неизвестен.

Скрипт `scripts/diagnose-photo-migration.cjs` содержит только чтение Firestore и
локальную проверку фото. Он не вызывает ни `runMigration`, ни `migratePlant`, ни очистку.
Тесты запускаются командой `npm.cmd run test:server`, без сети и серверных секретов.
