# Фотографии в Yandex Object Storage

Фотографии хранятся в приватном Yandex Object Storage, метаданные растений и
ключи объектов — в Firestore. Миграция production-фотографий из base64 завершена,
итоговые Firestore Rules опубликованы. Загрузка, отображение и постоянное удаление
проверены в production. Одноразовые скрипты переноса и очистки удалены;
клиентский fallback на старое `photo` удалён. Для проверки целостности фотографий
доступна команда `verify:photos`, описанная в разделе 7.

Для подготовки Vercel Preview без изменения production сначала прочитайте
[preview-readiness.md](preview-readiness.md). Preview не создаёт отдельную базу
или отдельные Firestore Rules: среду Firebase нужно изолировать явно.

## Текущая схема работы

- Приложение остаётся на React / Firebase Auth / Firestore / Vercel.
- Новое фото преобразуется в браузере в WebP (качество 0.8, длинная сторона
  не больше 1600 px, маленькие фото не увеличиваются). В памяти хранится Blob,
  в Firestore base64 больше не отправляется. Входной файл — до 25 МБ,
  оптимизированный — до 5 МБ. Неподдерживаемый браузером формат вызывает ошибку.
- `POST /api/photos` — единственная серверная точка для файлов. Firebase Admin
  проверяет подпись, срок действия, проект, отзыв ID Token и блокировку аккаунта.
  Сервер читает `plants/{id}` и сравнивает `userId` с UID из токена.
  Произвольный ключ от браузера для чтения/удаления не принимается.
- Загрузка: временный PUT URL на 5 минут → проверка размера, типа и реальных
  WebP-данных на сервере → сохранение отдельного файла → транзакция Firestore.
  Сервер повторно декодирует WebP и удаляет метаданные. URL загрузки указывает
  только на временный объект: повторный PUT не перезапишет опубликованное фото.
- При создании с фото документ появляется только после успешной загрузки.
  Повтор сохранения после потери ответа использует прежние ID растения и загрузки.
  Не закрывайте страницу до подтверждения: память повторной попытки сохраняется
  только на время текущей формы, а не после перезагрузки браузера.
- Новые фотографии сохраняются в Object Storage; в Firestore записывается
  `photoKey`, а не изображение или подписанный URL. Растение может быть без фото.
  Для показа сервер выдаёт GET URL на 10 минут; открытая карточка обновляет его
  заранее. При ошибке есть повтор. При отсутствии `photoKey` приложение не
  обращается к Object Storage и отображает растение без фотографии.
- Замена фото записывает новый `photoKey` вместе с полями формы.
  Если старое поле `photo` присутствует, API его не удаляет. Предыдущие
  объекты также сохраняются до окончательного удаления растения. Это намеренно
  предотвращает потерю фото при неопределённом результате сетевого запроса.
  Неиспользуемые версии занимают место; автоматический сборщик не добавлен.
- Эти же операции работают с существующим вишлистом.

Подписанная ссылка даёт доступ любому, кто её получил, до истечения срока.
Не публикуйте такие ссылки и не записывайте их в Firestore/логи/аналитику.

## 1. Переменные Vercel

Уже добавленные переменные должны быть **серверными**, без `REACT_APP_`:

```dotenv
YANDEX_ACCESS_KEY_ID=<static access key ID>
YANDEX_SECRET_ACCESS_KEY=<static secret key>
YANDEX_BUCKET_NAME=ficus-diary-photos
YANDEX_S3_ENDPOINT=https://storage.yandexcloud.net
```

Также нужны отдельные учётные данные **Firebase**, не сервисного аккаунта Yandex:

```dotenv
FIREBASE_PROJECT_ID=<тот же projectId, что у веб-приложения>
FIREBASE_CLIENT_EMAIL=<client_email из Firebase service account>
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"
ENABLE_PERMANENT_PLANT_DELETE=false
```

`false` — безопасное значение по умолчанию из `.env.example`. Для разрешения
постоянного удаления задайте серверную переменную
`ENABLE_PERMANENT_PLANT_DELETE` точно равной `true`: строчными буквами,
без внешних кавычек, пробелов и перевода строки. Отсутствующая переменная,
`false`, `TRUE` или `1` оставляют удаление выключенным. Для Production выберите
scope Production; значение применяется к новому deployment после redeploy.
Подробности удаления и обработки сбоев — в разделе 6.

Firebase Console → Project settings → Service accounts → Firebase Admin SDK.
Для существующего подходящего сервисного аккаунта получите приватный ключ.
Из скачанного JSON вручную перенесите `project_id`, `client_email`, `private_key`
в секретные переменные. JSON и PEM не помещайте в репозиторий.
В Vercel можно вставить настоящий многострочный PEM; буквальные `\n` сервер
тоже поддерживает. Кавычки из примера нужны для `.env.local`, в интерфейсе
Vercel не добавляйте внешние кавычки к значению ключа.

Сервисному аккаунту Firebase необходимы чтение/запись Firestore и чтение
пользователей Firebase Authentication для проверки отозванных токенов
(например, `roles/datastore.user` и `roles/firebaseauth.viewer`).
Firebase Admin обходит Firestore Rules, поэтому проверка владельца есть в API.

Для тестирования задайте переменные в **Preview** и локально. Убедитесь, что
Firebase web-конфигурация и Admin относятся к одному проекту. Production
настраивайте/публикуйте вручную после теста. Переменные применяются к новой
сборке/публикации Vercel. Проверьте runtime Node.js 24.x.

Аккаунту Yandex нужны операции GetObject, PutObject, ListBucket, DeleteObject
только для этого бакета. Создавать новые бакеты, базы, функции Yandex или
другие платные ресурсы не требуется. Публичный доступ к бакету не включайте.

## 2. CORS бакета — вручную

Yandex Cloud → Object Storage → `ficus-diary-photos` → **Безопасность → CORS**.
Добавьте правило:

| Поле | Значение |
| --- | --- |
| Allowed origins | `https://ficus-diary.ru`, `http://localhost:3000` и точный HTTPS origin выбранного Vercel Preview |
| Allowed methods | `PUT`, `GET`, `HEAD` |
| Allowed headers | `content-type` |
| Expose headers | `ETag` |
| Max age | `300` |

Origin — только протокол и домен/порт, **без** пути и завершающего `/`.
Если сайт фактически открывается на `www`, добавьте его отдельным origin.
Не используйте `*` для origins и не добавляйте `Authorization`: Firebase Token
отправляется только в `/api/photos`, а не в Object Storage. `Content-Length`
браузер выставляет сам; JavaScript не задаёт его вручную. `OPTIONS` обслуживает
Object Storage, добавлять этот метод в правило не нужно.

Если используете AWS CLI, эквивалент файла `cors.json` (замените preview origin):

```json
{
  "CORSRules": [{
    "AllowedOrigins": ["https://ficus-diary.ru", "http://localhost:3000", "https://YOUR-EXACT-PREVIEW.vercel.app"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 300
  }]
}
```

Необязательная альтернатива настройке через консоль; выполните сами с уже
настроенным локальным профилем AWS CLI для Yandex (не передавайте ключи в команду):

```powershell
aws --endpoint-url https://storage.yandexcloud.net s3api put-bucket-cors --bucket ficus-diary-photos --cors-configuration file://cors.json
```

Команда заменяет конфигурацию CORS бакета целиком: сначала сохраните имеющиеся
правила, если они есть. CORS не делает приватный бакет публичным.

## 3. Действующие Firestore Rules

В production опубликованы итоговые [firestore.rules](../firestore.rules).
Переходные правила и тесты старого состояния удалены после завершения миграции.
Основной набор тестов безопасности проверяет только окончательные правила.

Для Vercel Preview используйте отдельный тестовый Firebase-проект с итоговыми
правилами. Проверка правил без production доступна локально через
`npm.cmd run test:rules`. Preview с production-конфигурацией не изолирует данные.

Полная сверка полей и локальные тесты правил описаны в
[firestore-rules-audit.md](firestore-rules-audit.md).

История перехода описана в [production-release.md](production-release.md);
её указания о первом выпуске и временной блокировке удаления больше не описывают
текущее состояние. Деплой Vercel сам по себе не публикует Firestore Rules.
Будущие изменения правил сначала проверяйте в тестовой среде или эмуляторе.
В итоговом файле остальные коллекции закрыты по умолчанию.

Обязательно должны быть защищены:

- Чтение растений и обычные изменения — только владельцу, `userId` неизменяем.
- Браузер не меняет `photo`, `photoKey`, `_photoDeleting` и не удаляет документы
  напрямую. Серверные операции используют Admin SDK.
- `_photoUploads` недоступна клиенту ни для чтения, ни для записи.
- Документ с `_photoDeleting: true` нельзя восстановить/изменить из браузера.

Не оставляйте параллельное широкое правило `allow write: if true` или доступ
всем авторизованным: разрешения разных `match` объединяются. Старые вкладки
предыдущей версии не могут записывать base64 с итоговыми правилами —
обновите страницу. Существующие документы и их фотографии правила не изменяют.

## 4. Локальная разработка

Нужны Node.js 24 и npm. В PowerShell при запрете `npm.ps1` используйте `npm.cmd`.

```powershell
npm.cmd ci
Copy-Item .env.example .env.local
```

Если `.env.local` уже существует, **не перезаписывайте** его — добавьте недостающие
переменные вручную. Заполните публичную `REACT_APP_FIREBASE_*` конфигурацию и
серверные переменные из раздела 1. `.env.local`, `.vercel` и ключи игнорируются Git.
Не переименовывайте серверные секреты в `REACT_APP_*`: этот префикс встраивается
Create React App в браузерный JavaScript.

Запускайте фронтенд и `/api` через Vercel CLI из корня проекта:

```powershell
npx vercel dev --listen 3000
```

При первом запуске выберите существующий проект ficus-diary. В настройках проекта
должен быть framework preset **Create React App**, output directory `build`.
Команда может запросить вход в Vercel и установку CLI. Серверные секреты можно
задать также в окружении процесса. После изменения env перезапустите сервер.
Не запускайте `vercel --prod` во время локального теста.

`npm start` по-прежнему запускает только CRA: `/api/photos` в этом режиме нет,
поэтому для проверки загрузки нужен `vercel dev`. Добавьте `localhost` в
Firebase Authentication → Settings → Authorized domains, если его ещё нет.
Локальное приложение использует именно тот Firebase-проект, который указан
в env; локальный адрес сам по себе не изолирует данные от production.

Проверки без облачных записей:

```powershell
npm.cmd test -- --watchAll=false --runInBand
npm.cmd run test:server
npm.cmd run build
```

Серверные тесты используют имитацию Firestore/S3 и реальные локальные WebP-
преобразования. Они не подтверждают доступ реальных сервисных аккаунтов,
опубликованные Firestore Rules, CORS и работу Vercel runtime — это проверяется
на одном тестовом растении после ручной настройки.

## 5. Проверка одного тестового растения

Проверки с созданием, заменой и удалением выполняйте только на новом растении
в изолированной тестовой среде.

1. Проверьте, что публичные Firebase-переменные и Firebase Admin в Preview
   указывают на один **тестовый** Firebase-проект, а Object Storage — на тестовый
   бакет с настроенным CORS. Для проверки постоянного удаления задайте
   `ENABLE_PERMANENT_PLANT_DELETE=true` в этой среде. Автоочистки корзины нет:
   открытие страницы не удаляет старые записи независимо от их возраста.
2. Войдите в аккаунт, создайте **новое** растение «Тест Object Storage» с фото.
   После сохранения у него должен быть `photoKey`, без нового base64 в `photo`.
   В Network: `/api/photos` → PUT в Yandex → `/api/photos`; Firebase Token есть
   только в запросах к приложению. В браузере нет Secret Access Key/PEM.
3. Обновите страницу; дождитесь более 10 минут с открытой карточкой; фото должно
   продолжать показываться. Неподписанный URL объекта должен быть недоступен.
4. Замените фото у этого же тестового растения. В Firestore меняется `photoKey`.
   Старый объект остаётся. Отключите сеть во время следующей замены: форма и
   старое сохранённое фото должны сохраниться; повторите сохранение после сети.
5. Переместите тестовое растение в корзину и восстановите: фото остаётся.
   Снова переместите его в корзину и удалите вручную навсегда: API должен вернуть
   `{ "deleted": true }`, документ и объекты в префиксе растения удаляются.
   При выключенном флаге API вместо удаления возвращает 409; активное растение
   также нельзя удалить навсегда. Эти отказы покрыты серверными тестами.
6. Проверьте второй аккаунт: он не читает/меняет чужой документ через Firestore,
   а запросы upload/read/commit/delete к API с чужим plantId не дают доступа.
   Просроченный или недействительный Firebase ID Token должен возвращать 401.
7. Проверьте коллекцию и вишлист: фото по `photoKey` отображается на карточке
   и в предпросмотре вишлиста без поля `photo`; растение без фото тоже открывается.

## 6. Окончательное удаление и сбои

Перемещение в корзину и восстановление вообще не трогают файлы.
Автоматического удаления по возрасту, cron или фоновой миграции нет.

Растение хранится в корзине до удаления вручную. Постоянное удаление выполняется
через `POST /api/photos` с `{ "action": "delete", "plantId": "..." }` и Firebase
ID Token. В текущем коде `PERMANENT_DELETE_RELEASE_ENABLED=true`; обязательная
проверка `process.env.ENABLE_PERMANENT_PLANT_DELETE === 'true'` сохранена.
При отсутствии или другом значении env API возвращает 409 и оставляет растение
в корзине. Флаг позволяет отключить постоянное удаление без ослабления Rules.

Сервер проверяет владельца и корзину, ставит `_photoDeleting: true`, удаляет
объекты только из префикса владельца/этого растения (включая временные загрузки
и файлы предыдущих замен),
а затем удаляет документ Firestore. Если S3 недоступен, документ остаётся
заблокированным и повторное окончательное удаление продолжает операцию.
Восстановление в этот момент запрещено: часть файлов уже могла быть удалена.
Неправильный/чужой `photoKey` останавливает удаление до изменения документа.

Служебные записи `_photoUploads` сохраняются для идемпотентности. Автоматической
очистки этой коллекции нет. Не включайте lifecycle на весь `plants/`: там лежат
действующие фото и фотографии растений в корзине. Неиспользованные временные
загрузки могут остаться после сбоя или повторного PUT до истечения 5 минут;
это не возвращает доступ к удалённому растению. Для их очистки позже можно
вручную согласовать отдельную уборку. Версии объектов при включённом versioning
также не уничтожаются этим кодом безвозвратно — проверьте настройки бакета.

## 7. Проверка целостности фотографий

После завершения миграции сохранён [scripts/verify-photo-migration.cjs](../scripts/verify-photo-migration.cjs).
Он запускается отдельно, не вызывается при сборке или открытии приложения.

```powershell
npm.cmd run verify:photos -- --project YOUR_FIREBASE_PROJECT_ID
```

Нужен явный project ID, совпадающий с конфигурацией Firebase. Учётные данные
читаются из `.env.local` или окружения процесса; UID владельца указывать не нужно.
Скрипт проверяет все растения, включая вишлист и корзину, проверяет принадлежность
ключей и скачивает объекты через HEAD/GET с полной локальной декодировкой WebP.
Он не пишет в Firestore, не загружает и не удаляет объекты в Object Storage.

Код выхода `0` означает полный проход без ошибок и потенциальных проблем,
`1` — ошибку или незавершённую проверку, `2` — потенциальные проблемы.
Команда выполняет облачные чтения; локальные серверные тесты из раздела 4
проверяют verifier на заглушках без обращения к production.
