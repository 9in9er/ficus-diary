# Проверка фотографий после миграции

`scripts/verify-photo-migration.cjs` — отдельный скрипт только для чтения.
Он не запускает миграцию, не изменяет Firestore, не загружает и не удаляет объекты.
В Yandex Object Storage выполняются только `HeadObject` и `GetObject`, без подписанных URL.
Фотографии обрабатываются в памяти; локальные файлы изображений не создаются.

## Запуск в PowerShell

Из корня проекта, с Node.js 24 и существующими серверными настройками в `.env.local`:

```powershell
npm.cmd run verify:photos -- --project my-plants-app-8f6fc --expect-photo-keys 264 --expect-trash-base64 46
$LASTEXITCODE
```

Команда проверяет **все** документы верхнеуровневой коллекции `plants`: всех владельцев,
вишлист и корзину, страницами по 100, последовательно. UID вручную указывать не нужно.
`264` — ожидаемые 262 мигрированные фотографии и 2 ранее существовавших `photoKey`;
`46` — ожидаемое число растений в корзине с base64. Ожидания не ограничивают сканирование:
при несовпадении скрипт продолжит проверки и добавит потенциальную проблему в отчёт.
Если состав данных изменился, эти два необязательных параметра можно изменить или опустить.

Используются `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`,
`YANDEX_BUCKET_NAME`, `YANDEX_S3_ENDPOINT`, `YANDEX_ACCESS_KEY_ID`, `YANDEX_SECRET_ACCESS_KEY`.
До чтения проверяется совпадение явно указанного проекта с окружением и затем с Admin SDK,
а также база `(default)`. Эмуляторы не поддерживаются. Endpoint должен быть
`https://storage.yandexcloud.net` (допустим завершающий `/`).
Достаточные права хранилища — чтение HEAD/GET; право записи скрипту не требуется.

## Что проверяется

Для каждого ненулевого поля `photoKey`, включая корзину:

1. Непустой UID владельца, допустимый ID растения и точный путь
   `plants/<SHA-256(userId)>/<plantId>/photos/<UUID-shaped-name>.webp` по правилам приложения.
   Неверный путь фиксируется как ошибка; запрос к чужому или произвольному объекту не отправляется.
   Пустая строка и значения неверного типа в `photoKey` также считаются ошибками.
2. HEAD: объект доступен, размер — целое число от 1 байта до 5 МиБ,
   тип — `image/webp`, присутствует ETag.
3. GET с `IfMatch` из HEAD: объект можно полностью прочитать, ETag и размеры совпадают,
   фактический объём прочитанных байтов равен заявленному. Чтение ограничено по размеру и времени
   (60 секунд на HEAD, GET и чтение тела вместе, включая повторы SDK).
4. SHA-256 содержимого совпадает с `Metadata.sha256`, если метаданные присутствуют
   в HEAD или GET. У обычных фотографий, загруженных до миграции, этой метки может не быть.
5. Заголовок RIFF/WEBP и размер контейнера корректны; Sharp определяет WebP и **полностью
   декодирует пиксели**, а не только читает метаданные. Изображение должно иметь один кадр
   и размеры не более 1600 × 1600, как в приложении.

404 / `NoSuchKey` отражаются как `OBJECT_MISSING`; 401/403 — `OBJECT_ACCESS_DENIED`;
изменение объекта между запросами — `OBJECT_CHANGED`. Сетевые ошибки, тайм-ауты,
несовпадение размера/контрольной суммы и повреждённый WebP имеют отдельные коды.
Ошибка одной фотографии не останавливает остальные проверки. Ошибка страницы Firestore
останавливает сканирование и делает отчёт неполным.

## Отчёт

Для каждого документа выводится JSON с `plantId`, статусом и безопасными кодами ошибок/проблем;
для успешного объекта — также размер в байтах и размеры изображения. В конце выводится
JSON `summary` с итогами и `issues` — списком документов с ошибками или потенциальными проблемами.
Base64, ключи объектов, UID, имена растений, секреты, подписанные URL и исходные сообщения
ошибок SDK не выводятся. Для недопустимого ID выводится его SHA-256 вместо исходного значения.

| Поле `summary` | Значение |
| --- | --- |
| `totalDocuments` | Все прочитанные документы |
| `photoKeyFields` | Документы с полем `photoKey`, включая `null` и некорректные значения |
| `withPhotoKey` | Документы с ненулевым `photoKey`, включая пустые/некорректные значения, которые дадут ошибку |
| `photoAndPhotoKeyFields` | Документы, где физически присутствуют оба поля `photo` и `photoKey`, включая `null` |
| `base64AndPhotoKey` | Документы с base64 в `photo` и ненулевым `photoKey` |
| `withoutPhotoKey` | Документы без поля `photoKey` или со значением `null` |
| `trashPlants` | Все документы с непустым `deletedAt` |
| `trashWithBase64` | Растения в корзине с base64, независимо от `photoKey` |
| `trashWithBase64WithoutPhotoKey` | Растения в корзине с base64 без ненулевого `photoKey` |
| `activeBase64WithoutPhotoKey` | Растения вне корзины с base64 без ненулевого `photoKey` — потенциальная проблема |
| `attemptedObjects` | Объекты, для которых начата проверка HEAD/GET после проверки пути |
| `verified`, `verifiedBytes` | Успешно проверенные объекты и суммарное число прочитанных байтов этих объектов |
| `failedPhotoKeys` | Документы с ненулевым `photoKey`, не прошедшие проверку, включая ошибки пути |
| `errors`, `errorsByCode` | Число ошибок документов и сканирования, разбивка по кодам |
| `potentialProblems`, `problemsByCode` | Число замечаний и разбивка по кодам; у документа может быть несколько замечаний |
| `scanComplete` | Прочитаны все страницы Firestore |
| `checksPassed` | Полный проход без ошибок и потенциальных проблем |
| `startedAt`, `completedAt` | Время начала и окончания в UTC |

Base64 для статистики определяется по префиксу `data:image/...;base64,`, как в миграции;
содержимое старого `photo` не декодируется и не сравнивается с новым изображением.
Наличие одновременно старого фото и ключа — ожидаемый результат миграции, а не ошибка.
Base64 в корзине также считается отдельно и сам по себе не является проблемой.
Замечания возникают при активном base64 без ключа, `_photoDeleting`, отсутствии всех ключей
или несовпадении переданных ожидаемых количеств.

При неизменных данных ожидаются `withPhotoKey: 264`, `verified: 264`, `failedPhotoKeys: 0`,
`trashWithBase64: 46`, `errors: 0`, `potentialProblems: 0`, `scanComplete: true`, `checksPassed: true`.
Количество `base64AndPhotoKey` зависит также от наличия старого `photo` у двух растений,
которые уже имели ключ до миграции.

Коды выхода: **0** — полный проход без ошибок/замечаний; **1** — ошибки или неполный проход;
**2** — только потенциальные проблемы. При `scanComplete: false` счётчики относятся
лишь к прочитанной части коллекции. Даже успешная проверка не означает, что base64 корзины
без `photoKey` можно удалять: для таких документов новое фото ещё не подтверждено.

Проверка отражает состояние во время прохода: Firestore и Object Storage не имеют общей
транзакции, а страницы читаются последовательно. На время итоговой проверки приостановите
редактирование фотографий, миграцию и удаление растений. После последующих изменений
проверку следует повторить. Скрипт не удаляет base64 и не выдаёт разрешения на очистку.

## Локальные тесты

```powershell
npm.cmd run test:server
```

Тесты используют Firestore/S3 в памяти и реальные локальные WebP через Sharp. Проверяются
полный проход 262 + 2 + 46, пагинация, счётчики, чтение корзины, правильность пути,
отсутствующие и недоступные объекты, ошибки HEAD/GET, тайм-аут, неверные размеры,
контрольные суммы, неверный MIME, анимация и повреждённый WebP, у которого ещё читаются
метаданные. У тестовых адаптеров нет операций записи, а S3-адаптер принимает только HEAD/GET.
Проверяется также отсутствие чувствительных данных в отчёте и диагностике CLI.
